# Вариантность типов в Python: учебный проект

Этот проект нужен для демонстрации трёх видов вариантности:

- инвариантность
- ковариантность
- контравариантность

Идея простая: показать, что не все `Generic[T]` ведут себя одинаково. В языке со статической типизацией это влияет на то, какие присваивания допустимы, а какие нет.

## Что внутри проекта

```text
pract_4/
├── containers.py               # базовые generic-классы: Stack, ReadOnlyStack, Handler
├── models.py                   # минимальная иерархия Animal -> Dog / Cat

├── demo_invariant_fail.py       # нарушение инвариантности

├── demo_covariant_fail.py       # нарушение ковариантности

```

## Как читать проект

### 1) Инвариантность
Файл: `demo_invariant_ok.py`, `demo_invariant_fail.py`

`Stack[T]` и пишет, и читает. Значит, он должен быть инвариантным.

- `Stack[Dog]` нельзя использовать как `Stack[Animal]`
- `Stack[Animal]` нельзя использовать как `Stack[Dog]`

Потому что это хранилище, которое может и добавлять, и извлекать элементы.

### 2) Ковариантность
Файл: `demo_covariant_ok.py`, `demo_covariant_fail.py`

`ReadOnlyStack[T_co]` только читает данные, поэтому безопасно сделать его ковариантным.

- `ReadOnlyStack[Dog]` можно передать туда, где ждут `ReadOnlyStack[Animal]`
- обратное направление — нельзя

Это демонстрирует главный принцип: более узкий тип можно использовать там, где ожидается более общий тип, если объект только читается.

### 3) Контравариантность
Файл: `demo_contravariant_ok.py`, `demo_contravariant_fail.py`

`Handler[T_contra]` принимает объект и ничего не возвращает. Это типичный consumer.

- `Handler[Animal]` можно использовать там, где ждут `Handler[Dog]`
- обратное направление — нельзя

То есть обработчик более общего типа подходит и для более частного случая, но не наоборот.

## Что именно демонстрируют `_fail` файлы

Это ключевая часть проекта.

- `mypy` должен показать ошибки
- обычный `python` может их не заметить до момента реального использования

### Пример 1: тихая ошибка
Файл: `demo_covariant_fail.py`

В коде на Python всё выглядит нормально, но логически переменная объявлена как `ReadOnlyStack[Dog]`, хотя по факту в ней лежит `Animal`.

Это классический источник скрытых багов.

### Пример 2: явный runtime-crash
Файл: `demo_contravariant_fail.py`

Здесь нарушается контравариантность настолько явно, что в рантайме возникает:

```python
AttributeError: 'Cat' object has no attribute 'bark'
```

Это хорошая демонстрация: статическая проверка нужна не для красоты, а чтобы ловить реальные ошибки до запуска программы.

## Что важно показать на занятии

1. `mypy` не "придирается просто так" — он защищает от логически неверных присваиваний.
2. `python` не проверяет типы во время выполнения.
3. Условие "код запустился" и "код типобезопасен" — не одно и то же.
4. Вариантность — это не теория ради теории, а правило, которое помогает понять, где безопасно передавать обобщённые значения между частями программы.

## Полезная команда

```bash
uv run bash run_demos.sh
```

Эта команда запускает все примеры подряд и печатает и вывод `mypy`, и вывод `python` для каждого файла. Именно так удобнее всего объяснять разницу между "возникла ошибка в типах" и "выполнение прошло, но логика может быть неверной".
